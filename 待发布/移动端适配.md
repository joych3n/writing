# 移动端适配

关于移动端适配的调研与方案选择

## 前置知识

### rem 适配原理

根据屏幕宽度动态修改 html 的 font-size 的值，1rem 等于这个值 ，所以 rem 能适配不同屏幕。比如把屏幕分 10 份，375px 的屏幕，font-size 会被修改 37.5px，在 430px 屏幕是，

### vw 适配原理

vw 是视口宽度的百分比，1vw 等于屏幕宽度的 1% ，所以 vw 能适配不同屏幕。

## 需要考虑的因素

1、好开发，看到的尺寸直接写
2、好维护，方便看懂，方便修改
3、效果好，像素级还原设计稿

## 被否掉的方案及原因

1、postcss 的插件，px 转 rem 或 vw ，为了排除 PC 样式，增加很多标记代码。（适合独立 H5 项目，最佳实践）

2、媒体查询写法，首先需要添加移动端类名，其次原子化和样式混合写一起，不优雅（适合非 css 原子化的项目）。

3、口算 vw 直接手写，缺点是效率低，无法像素级还原设计稿（适合没有 UI 图的项目）

4、rem 方案，为了避免影响 PC 端，当屏幕宽度小于 768 时，根据屏幕宽度动态修改 html 的 font-size。
第一个缺点：和 方案 1 一样，为了排除 PC 样式，增加很多标记代码。
第二个缺点：
以 375px 屏幕宽度为例，（vw/clentWidth）*37.5px
屏幕宽度分成 10 份，每份宽度 37.5px ，font-size 设为 10 分之一，10rem 就是撑满全屏，兼容其他 UI 框架，但是不直观。
（vw/clentWidth）*10px 10px 37.5rem，直观，但是如果要进入 UI 框架存在兼容问题。

根据我们的项目情况：

1、同时存在 PC 端和移动端

2、unocss 原子化写法

3、会影响老代码的 rem 写法转 px

4、会影响继承的字体大小的样式

## 最终方案：设计一个 unocss 转换规则，直接写设计稿尺寸，自动转换成 vw。

unocss 转换规则：

```js
rules: [
  // 宽度：w-d150 => width: (150 / 375 * 100)vw
  [
    /^w-d(\d+)$/,
    ([, d]) => {
      const n = Number(d);
      return { width: `${(n / DESIGN_WIDTH) * 100}vw` };
    },
  ],
  // 内边距：p-d16 => padding: ...
  [
    /^p-d(\d+)$/,
    ([, d]) => {
      const n = Number(d);
      return { padding: `${(n / DESIGN_WIDTH) * 100}vw` };
    },
  ],
];
```
